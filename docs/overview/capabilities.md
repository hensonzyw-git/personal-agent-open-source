## 1. 当前能力与验证边界

### 1.1 如何阅读状态

本文采用四种说明，而不是笼统地把功能标记为“已完成”：

| 标记 | 含义 |
| --- | --- |
| **已有实现** | 存在对应源码、协议或测试；不自动代表所有调用路径已接通 |
| **有限实测** | 在指定设备、版本、输入和授权范围内有运行或验收记录 |
| **待贯通** | 组件或协议已存在，但完整用户路径、阶段推进或真实边界仍需实现和验证 |
| **规划** | 目标、设计方向或后续工作；不是当前产品承诺 |

### 1.2 能力地图

| 能力 | 当前边界 | 不能据此推出的结论 |
| --- | --- | --- |
| iOS 聊天、Timeline、服务端会话与上下文管理 | 已有实现；原单用户环境有真机使用与部署记录 | 不代表已支持多用户、任意设备或任意规模 |
| Finance 查询、受控写入、人工核对与定时核对 | 已有实现；原环境有端到端闭环记录，包含旅行场次聚合等增量功能 | 不代表公开版附带可用账本、生产凭据或其他人的业务规则 |
| ADK 运行时、模型适配和工具调用治理 | 已有实现；部分真实模型与真机路径已有验证 | 不代表所有模型、提示词组合与长上下文场景均已通过评测 |
| 公共网页搜索、正文提取 | 已有实现；原环境按设备与能力开关开展过受控试点 | 不等于通用浏览器控制或任意网站操作 |
| 图片输入和 Timeline 图片展示 | 已有实现与部分真机验收；原环境存在明确记录的单用户安全例外 | 不代表所有图片理解质量和完整媒体安全链路均已验证 |
| Apple Calendar | 有实现和隔离验收构建记录 | 尚不能据此宣称真实后端、真实 EventKit 写入和正式 App 的完整链路已验收 |
| DAL 状态、审批绑定、动作生命周期、恢复、执行配置 | 已有实现和离线验证记录 | 不等于从手机需求到交付的完整自动工作流已可用 |

| DAL 规划／编码／审查角色 | 有配置及分别运行的探针记录 | 三个探针通过，不等于三个角色已串成完整交付链 |
| 手机发起 DAL 需求、项目授权、报告展示 | 已有入口与授权实现 | 完整手机研发交付未在本轮端到端验收 |
| 分阶段规划、编码、审查、提交、PR 和用户交付验收 | 已有自动工作流、阶段和提交审查实现；**完整交付待验收** | GitHub adapter 存在，不等于阶段成功后会自动形成合法发布意图 |
| 知识库、HealthKit、衣橱／穿搭、长期个人记忆等 | **后续方向**，按能力逐项设计和验证 | 不是当前 Finance 或 DAL 验收的自然延伸 |

原仓库的历史状态入口为 `PROJECT_STATUS.md`。其中保留了不同阶段的记录，阅读时必须结合日期、后续覆盖说明与实际源码；历史“待批准”“尚未合并”等措辞不应覆盖之后已经发生的事实。

### 1.3 一个特别重要的完成度边界

DAL 当前真实部署证据包含：ECS 控制面与 Mac mini Worker 协作执行一个受控角色、保存执行回执、回读产物摘要、验证进程退出，并确认后续轮询没有重复发起同一调用。

**该路径使用 `report_only`：报告完成，不代表 Feature 阶段推进，更不代表需求交付。** 源码明确拒绝将此类结果按普通 Feature 结果消费；动作结果消费路径也不能拿一个“已消费”标志冒充尚未支持的阶段推进。

这不是文案上的保留，而是实现中的边界。参见 [action_lifecycle.py](../../src/personal_agent_dal/machine/action_lifecycle.py) 的 `consume_result`。

## 2. 个人 Agent：从一句话到业务结果

### 2.1 正常处理路径

```mermaid
flowchart LR
    A["用户输入"] --> B["设备身份与请求锚定"]
    B --> C["持久操作 / 上下文组装"]
    C --> D["模型理解与工具意图"]
    D --> E["服务端策略与 schema 校验"]
    E --> F["受控工具 / 业务连接器"]
    F --> G["事实回读与证据记录"]
    G --> H["结构化结果与界面展示"]
```

模型看到的是与当前请求相关、当前设备获准使用的工具，而不是账户能调用的全部底层 API。服务端可以拒绝不支持的参数、权限不足的操作、过期请求和无法满足安全条件的调用。

对于写操作，系统要解决的不只是“把参数传过去”，还包括稳定幂等键、重复判断、写入策略、审计关联和外部结果核对。模型说“记好了”不能代替真正的写入证据；外部结果不确定时，应保留不确定性而非猜测成功或直接重发。

日常业务的授权粒度由各域规则决定：**DAL 的文档审批门不等于所有 Finance 单笔写入都必须多一次弹窗；Finance 的已有授权也不能扩展成开发或部署授权。**

实现入口：[host.py](../../src/personal_agent/runtime/host.py)、[policy](../../src/personal_agent/policy/)、[mcp_client](../../src/personal_agent/mcp_client/)、[personal_data_mcp](../../src/personal_data_mcp/)。

### 2.2 模型运行本身也要被管理

运行时记录请求、任务绑定、模型尝试、工具步骤、预算与结果证据。新的模型调用前重新检查设备状态和可用能力，而不是在会话开始时检查一次后永久信任。

预算在调用前预留，工具清单和策略有对应的快照或摘要；取消、权限变化和容量不足有明确失败路径。调用结果必须符合当前运行合同，不能把不合格响应静默修补后当成成功。

界面展示的是可验证的执行进度，例如正在理解、调用工具、等待数据源和核对结果；不是把模型隐藏推理文本当作工作日志。

依据：[DurableRunHost](../../src/personal_agent/runtime/host.py)、[运行持久化](../../src/personal_agent/runtime/run_repository.py)、[调用结果见证](../../src/personal_agent/runtime/response_witness.py)。

## 3. 数据、上下文与记忆

### 3.1 保留历史，不等于每轮发送全部历史

Timeline、Session、运行记录和模型当前上下文分别承担不同职责。系统需要保存可追溯历史，也需要为每次调用构造有界、相关的上下文。

当前实现包括会话上下文构建、压缩及输入预算管理。当前请求、必要约束和待处理状态，与一般历史、摘要和网页材料分别处理；超出预算时可以减少非关键历史或正文投影，但不能悄悄删掉必要条件后继续执行。

已实现的上下文管理**不等于**一个已经完整产品化、可长期自主维护的个人记忆系统。长期记忆的来源、纠错、失效、遗忘和跨任务使用仍需独立治理。

代码入口：[context](../../src/personal_agent/context/)、[input_budget.py](../../src/personal_agent/runtime/input_budget.py)、[host.py](../../src/personal_agent/runtime/host.py)。

### 3.2 不可信材料不能成为系统指令

聊天历史、网页正文、Issue、PR 评论和仓库文件都可能包含对模型的诱导文本。系统应把这些材料作为待处理的数据，而不是允许它们覆盖策略、创建审批或修改执行配置。

降低风险的关键不是只加一句“忽略恶意提示”，而是让实际动作仍需通过当前身份、工具合同、授权绑定和执行边界。提示词是一层防护，不是权限系统。

### 3.3 业务工具优先于任意数据访问

MCP 在这里是受治理的工具边界，不是默认开放数据库、shell 或任意文件访问的通道。

优先暴露具有明确业务语义的工具，由连接器负责字段映射、分页、聚合、幂等和事实源交互。查询“全部记录”不能只返回第一页；任务“不完整”与数据“确实为空”必须区别对待。

知识库方向沿用 `raw/` 与 `wiki/` 的设计分工：自动收集先进入原始收件区，整理后的知识和破坏性修改需要更严格的审核。这是后续域的设计边界，不是当前已完成的知识库产品声明。
