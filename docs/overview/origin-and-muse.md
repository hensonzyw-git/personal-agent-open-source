## 项目起源：早于 Muse 发布的独立探索

**本项目在 2026 年 7 月已经启动。原始开发仓库的首个 Git 提交记录为 2026 年 7 月 23 日，早于 Meta 在 2026 年 9 月 8 日公开发布 Muse。** 公开仓库保留了经脱敏的原始开发提交关系和 Git 时间；仓库创建时间仍是公开准备时。

| 时间 | 事件 | 依据与口径 |
| --- | --- | --- |
| 2026-07-23 | 原始项目已提交 Personal Agent PRD 与 ECS 基线 | 维护者核对了原始仓库根提交的日期、标题和无父提交属性；公开提交标识因脱敏而改变，原始标识不发布 |
| 2026-09-08 | Meta 公开发布 Muse | [Meta 官方发布说明][M1] |
| 后续公开整理 | 在脱敏历史之上添加公开文档与合成评测集 | 新仓库的创建日期不代表项目启动日期 |

我是一名产品经理，最初想解决的是自己的个人数据与日常使用问题：让手机上的自然语言交互，经由自己的 ECS 服务端，真正连接到可控的业务工具和数据。项目先围绕实际个人场景落地，再在开发过程中逐步形成 DAL，用来管理需求、设计、编码、审查和交付。

**本项目不是 Muse 的复刻、移植或开源实现，也不是在 Muse 发布后以复现它为目标启动的项目。** 对我而言，这是个人项目与大厂应用在“长期服务个人、能够实际行动的 Agent”方向上的不谋而合，而不是相同产品的两种发行方式。

两者的起点不同：本项目从“给自己用、连接自己的数据，并让个人能持续建设这套系统”出发；Muse 的公开定位则是让广泛用户无需技术经验就能使用个人 Agent 的产品。[M1] 对照用于解释方向与取舍，不用于把本项目包装成一个已经成熟的替代品。

> 时间比较仅说明本项目早于 **Muse 的公开发布**，不代表早于 Meta 的内部研发，也不构成原创性或技术优先权的证明。Meta 的安全设计文章另外提到其团队从 2026 年初开始开发和内部使用 Muse。[M3] 本项目不会把“更早留下自己的开发记录”写成“比 Meta 更早做出同等产品”。

## 1. 项目定位

### 1.1 要解决什么问题

这个项目探索的不是“如何给聊天界面接上一个模型”，而是：

**当一个 Agent 长期接触个人数据、执行真实操作，并参与自己的软件开发时，怎样让它始终可理解、可约束、可追溯，并在出错后可恢复？**

项目由两条相互关联、但边界独立的链路组成：

| 链路 | 解决的问题 | 主要组成 |
| --- | --- | --- |
| **Personal Agent** | 把自然语言请求转化为受控的个人数据查询与业务操作 | iOS App；ECS 上的 Agent Runtime、Context Builder、Policy、MCP Client、业务连接器、审计与定时任务 |
| **Development Agent Loop（DAL）** | 把软件需求推进为经过规划、授权、编码、验证和独立审查的可审核交付 | ECS 上的工作流、状态机、审批、队列与 GitHub 控制面；Mac mini 上的开发 Worker、运行适配器与验证器 |

**本文中的 DAL 是 Development Agent Loop，不是 Data Access Layer。**

日常 Agent 不依赖 DAL 才能工作。DAL 是一条独立的研发基础设施轨道：它的长期价值是帮助个人持续构建、维护自己的 Agent 能力，而不是让日常聊天模型获得任意修改系统和生产环境的权限。

### 1.2 项目的核心选择

**模型负责理解和提出行动，系统负责判断是否允许行动、记录事实和决定流程状态。** 模型可以更换；任务状态、权限、业务规则和交付证据不应随某个模型会话的结束而丢失。

**围绕真实个人场景构建，而不是先抽象一个无所不能的平台。** Finance 是已经落地的业务闭环；Calendar、知识库和其他个人数据域按独立边界扩展。

**把“开发过程”也作为产品来设计。** PRD、技术方案、审批、审查意见、执行记录和恢复路径，都应有明确对象和生命周期，而不是只存在于多段聊天记录里。

**自动化不等于放弃控制。** 系统可以自动执行已经批准的步骤，但不能自行改变需求范围、放宽权限、伪造审批，或把“产出了一份报告”解释为“已经交付并上线”。

架构与协作原则见 AGENTS.md（原仓库路径：`AGENTS.md`）；运行时入口见 [personal_agent](../../src/personal_agent/)，开发闭环入口见 [personal_agent_dal](../../src/personal_agent_dal/)。

### 1.3 非目标

本项目当前不是多租户 SaaS、通用 Agent 商店、开箱即用的个人助理发行版，也不是一个不经审批就能自行合并和部署代码的“全自动程序员”。

它不保证任意模型都能互换使用，不把第三方模型、API 或订阅额度纳入项目可控范围，也不以“完全本地”“绝对安全”或“零人工介入”作为现状描述。

## 2. 与 Muse 的异同

这里的 Muse 指 **Meta 于 2026-09-08 发布的个人 AI Agent 产品**，不是同名应用或仅指其底层模型。Muse 公开发布日期于 **2026-09-23**再次核对；其余对比材料整理于 **2026-09-22**；以下基于官方产品与设计说明，不是独立性能或安全评测。[M1]

### 2.1 相似的方向

Muse 同样面向持续性的个人任务，而不只是即时问答；官方设计包含长期目标、主动跟进和记忆，也提供自建工具的能力。[M1] [M2]

因此，本项目不以“只有我们才有长期 Agent、审批或自我扩展”作为差异。更重要的问题是：**系统由谁建设和运营、哪些控制逻辑能够被直接审阅，以及软件变更怎样从需求变成有证据的交付。**

### 2.2 不同的产品与工程侧重点

| 维度 | Muse：官方公开描述 | Personal Agent：本项目边界 |
| --- | --- | --- |
| 产品形态 | 面向用户的托管个人 Agent 产品。[M1] | 单用户系统的代码与架构参考，不提供可直接部署的公开发行版 |
| 执行环境 | 专属云端 VM，包含浏览器等执行能力。[M1] | ECS 承载日常 Agent 与 DAL 全局控制面，家庭 Mac mini 执行受控开发任务；不是纯本地系统 |
| 长期工作与记忆 | 产品强调持续跟进、主动性及可管理的记忆。[M2] | 已有会话、上下文和持久执行基础；完整长期记忆与目标系统仍是后续方向 |
| 工具扩展 | 可以编写工具与自定义连接器。[M2] [M3] | DAL 目标是让新能力经过需求、设计、授权、验证与交付流程，而不只生成代码 |
| 权限控制 | Sentinel 与执行域分离，负责外部动作和网络出口许可。[M3] | 侧重业务 scope、状态／产物审批绑定、capability、租约、CAS 和受控执行；两者隔离层级不能直接等同 |
| 用户审批 | 有独立于普通对话的审批机制。[M3] | 重点公开审批如何绑定版本、内容、当前状态及具体动作，防止旧批准作用于新产物 |
| 软件交付 | 官方资料展示代码与工具构建能力，但本对比未确认其公开了与 DAL 等价的 PRD—阶段审查—交付协议。[M2] [M3] | 把该协议本身作为重点开放内容；同时承认完整自动链路尚未验收 |
| 模型与执行组合 | 本次资料不足以确认其具备与本项目相同的角色／runtime／placement 配置边界 | 以可替换适配器与版本化配置为方向；当前支持程度以已实现方案和准入为准 |

**这不是“开源版 Muse”，也不是对 Muse 的复刻声明。** 本项目的定位是展示一种个人可建设、可审阅、可持续演进的工程实现；不声称比 Muse 更成熟、更安全、更便宜或具有更高任务成功率。

官方产品陈述、安全设计和本项目自身的局部验证，属于不同证据，不能直接拼成优劣排名。
