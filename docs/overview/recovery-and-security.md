## 1. 外部副作用、暂停与故障恢复

### 1.1 先记录意图，再调用外部系统

持久状态与外部调用之间采用以下边界：

```text
校验当前授权和版本
  → 持久化意图 / 领取派发权
  → 提交事务
  → 执行外部调用（不持有数据库事务）
  → 持久化结果与观察证据
  → 控制面重新核验
  → 在事务中接纳结果与推进状态
```

不把网络请求、模型调用或子进程放在一个长数据库事务中。可重试的数据库单元必须不包含已可能发生的外部副作用，否则一次数据库重试可能变成两次真实操作。

### 1.2 `unknown` 是必要状态

例如：控制面已经授予派发权，Worker 发起模型调用，随后连接中断。控制面不知道调用是否完成，甚至不知道它是否仍在运行。

这时不能直接解释为“没有执行”，也不能把队列重新领取等价成安全重试。当前动作恢复会保留证据并将失去可确认归属的执行停放为 `unknown`，通过可信回读收集观察，而不是自动重新发起 provider 调用。

回读得到“进程已结束”也不等于 Feature 可以成功推进：还需要产物验证、授权核对及相应结果接纳。必要的新尝试应走显式续批或 replacement，并保留与旧尝试的关系。

依据：[action_recovery.py](../../src/personal_agent_dal/machine/action_recovery.py)、[resume_authority.py](../../src/personal_agent_dal/machine/resume_authority.py)、[resume_dispatch.py](../../src/personal_agent_dal/machine/resume_dispatch.py)。

### 1.3 典型失败如何处理

| 情况 | 处理原则 | 禁止的捷径 |
| --- | --- | --- |
| 需求不明确或仓库不确定 | 停在澄清或人工决策，保留当前任务 | 让模型猜一个仓库后直接修改 |
| Provider 认证失败或额度不足 | 明确阻塞；按已批准配置处理 | 静默换供应商、降低 reviewer 要求或新开付费资源 |
| 网络短暂失败 | 仅对满足重放语义的操作进行有界重试 | 默认认为所有请求都可重发，尤其是会领取新任务或产生写入的请求 |
| 派发后失联 | 保存派发标记与证据，进入核对路径 | 自动当作“未执行”再次调用 |
| 旧 Worker 晚交结果 | 保存可用观察，检查 owner、fence、epoch | 因结果格式正确就接受已失效的权限 |
| 同一尝试返回不同摘要 | 暴露冲突，不覆盖原证据 | 选其中一个“看起来更成功”的结果 |
| 用户暂停或取消 | 更新执行门、退休相关可用授权，保留在途与历史事实 | 把停止未来执行说成已经回滚远端写入或杀死所有进程 |
| GitHub 写入结果不明 | 按准确目标回读，核对是否发生 | 重复创建 PR、重复写入或猜测远端状态 |
| 自动修复不收敛 | 在预算边界转人工或重新规划 | 无限 review/fix，直到模型给出 PASS |

### 1.4 回执不是成功的同义词

回执可以证明某个请求已处理、某次观察已记录、某个动作被拒绝，或者某份证据已接纳。其含义取决于 schema、绑定对象和结果代码，而不是“存在 receipt”这件事本身。

系统通过幂等、CAS、派发标记、租约和外部核对控制重复与不确定性，**不把这些机制包装成跨任意第三方系统的通用 exactly-once 保证**。

## 2. 安全与隐私边界

本项目的原则是最小权限、明确授权、可核对的副作用以及失败时默认拒绝继续，但这不构成安全认证或全面审计结论。

**自托管不等于数据完全不出机器。** 使用远程模型、搜索或外部连接器时，获准的上下文和请求仍会离开自己的基础设施；需要分别理解发送内容、服务提供方和保留策略。

**源码公开不等于公开生产环境。** 个人数据、真实账本、健康原始数据、设备信息、密钥、证书、登录缓存、数据库、备份、真实资源标识及未经审阅的执行日志不属于公开版本的运行材料。

**安全规则的存在不等于所有部署路径都已经验证。** 媒体处理、CLI 沙箱、凭据隔离与网络出口尤其依赖实际部署；某个单用户试点接受的例外，不能作为面向其他用户的默认安全方案。

本项目不建议把未知来源的代码直接连接到真实个人数据、生产凭据或可写入的外部账户。改造与实验应先使用隔离环境和合成数据，逐项验证授权、拒绝和恢复路径。
