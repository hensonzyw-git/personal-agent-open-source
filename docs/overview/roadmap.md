## 1. 未来规划

### 1.1 排序原则

下一阶段的最高开发优先级是**搭建可管理的 Memory 模块**。现有上下文组装中的 `MemoryCandidate` 只接收传入的记忆候选，尚不能独立完成长期记忆的保存、检索和治理。Memory 建立后，再优先跑通从用户入口到交付验收的完整开发流程。

以下里程碑按这一优先顺序组织；M0 是公开版本的发布准备，不占用下一阶段的开发优先级。各里程碑是建议路线，不表示已经批准具体实现，也不预设发布日期。Memory 的本轮产品范围和技术方案仍须先分别确认。

### M0 · 建立可信的公开参考版本

**目标：** 公开内容可读、可追溯，且不会让读者误判部署和成熟度。

**交付范围：** 独立公开代码快照、完成审阅的示例与文档、明确许可证、有效的代码链接、能力状态表和公开变更说明。删除或改写个人身份、生产资源、环境路径和历史交接中的敏感内容；冻结合同与测试样本的修改保持一致。

**验收条件：** 从全新检出的公开仓库可以找到文档引用的源码；没有指向私有资源的必要依赖说明；安全审阅与许可决定完成；任何尚不可复现的测试或运行环节均有明确说明。这个里程碑仍不承诺一键部署。

### M1 · 搭建可管理的 Memory 模块

**目标：** 让对单用户有持续价值的事实和偏好可以跨会话使用，同时保留来源、纠错和遗忘能力。

**交付范围：** 先明确记忆类型、来源、写入与检索边界，再实现受控保存、检索、纠错、失效和删除，并与现有上下文组装衔接。敏感信息的保留和跨任务使用需要明确授权与可审计记录；具体自动提取策略由本轮 PRD 和技术方案确定。

**验收条件：** 经确认的记忆能在后续会话中按范围召回且可追溯来源；纠错、失效或删除后，旧内容不会继续进入上下文；未经授权的敏感内容不会被写入或召回。离线测试与真实使用证据分别记录，不以已有 `MemoryCandidate` 接口代替模块验收。

### M2 · 跑通第一条真实开发需求的纵向闭环

**目标：** 不再只证明 Worker 能执行一次，而是证明一项用户需求能被可靠推进并验收。

**交付范围：** 手机需求进入、项目范围确认、版本化 PRD、结构化审批、技术方案与必要人工门、受控编码、确定性验证、独立审查、交付包以及手机结果展示。首个完整任务选择真实、范围有限的 Finance 或横向能力需求，而不是只重复合成探针。

**验收条件：** 同一个 Feature 串起需求、批准文档、候选版本、验证、审查和用户验收；记录所有人工替代步骤；不能靠手工 SQL 改状态或人工传递产物冒充自动链路；明确区分交付、合并与部署终点。

### M3 · 补齐阶段化推进和真实故障恢复

**目标：** 从“顺利时走通一次”推进到“中断后仍能正确处理”。

**交付范围：** 多阶段依赖、阶段提交、配置变更、暂停／取消／续批、额度与认证失败、ECS 服务重启／暂时不可达、Mac mini Worker 重启、两端重连、旧结果晚到、外部写入未知及受控恢复。重点验证每个持久边界和真实运行边界。

**验收条件：** 在指定故障点中断后，不重复执行不确定副作用，不让旧批准或旧租约复活，不吞掉冲突证据；用户能从正常入口理解阻塞、作出决定并恢复。每一种恢复结果对应准确产物和回执，而不是只有成功日志。

### M4 · 将 DAL 整理为可理解、可迁移的构建层

**目标：** 保留个人定制能力，同时降低别人理解和改造架构的成本。

**交付范围：** 梳理工作流、角色、runtime、placement 与 policy 的配置边界；完善适配器能力检查、配置快照、运行证据和协议文档。探索把与个人业务无关的控制面合同、执行器接口和合成示例独立整理出来。

**验收条件：** 新增一种受支持的角色配置或 Worker 能力，不需要改写核心授权逻辑；不支持的组合可明确拒绝；示例不会把作者的账户、机器和特定模型配置作为默认前提。

这一方向首先是**可读、可研究、可改造**，不自动转向多租户平台或承诺完整安装产品。

### M5 · 完成下一批个人能力的真实闭环

**目标：** 在底层治理可用后，按独立业务合同扩展，而不是把域名列进工具列表就宣布支持。

| 方向 | 下一步重点 | 验收边界 |
| --- | --- | --- |
| Calendar | 正式客户端、服务端与真实 EventKit 的连接；同步与恢复 | 真实查询／写入、拒授权、重复处理、时区与中断场景可核对 |
| 知识库 | 原始收集、来源追踪、整理与确认式发布 | 来源可回溯；自动整理不能越权覆盖已确认知识 |
| HealthKit 等敏感数据 | 最小字段、只读优先、独立授权与隐私边界 | 数据获取、保留与使用范围可解释；不默认扩展高风险行动权限 |
| 衣橱／穿搭等个人域 | 先解决数据源可达性和真实使用流程 | 新域不会破坏已有 Finance、Calendar 与权限规则 |

既有知识库、健康和衣橱方向的产品细节仍需各自 PRD 与技术方案；Memory 模块的基础建设已前移至 M1。

### M6 · 在治理边界内形成持续演进能力

**目标：** 让个人 Agent 的改进可以由真实使用反馈触发，再进入可审阅的软件开发流程。

**交付方向：** 从失败记录、重复人工操作和能力缺口形成候选需求；由用户确认优先级和范围；通过 DAL 实现、验证与交付；新能力正式启用前完成独立授权与必要上线检查。

**验收条件：** 系统可以提出并执行已批准的改进，但不能修改自己的安全边界以绕过审批；一项能力从提出、实现到启用都有版本、来源、验证和回滚／停用考虑。

这里的“持续演进”是受治理的软件工程，不是允许模型自行重写控制面的授权规则。

### 1.2 用什么衡量进展

后续记录应先回答“记忆能否被正确保存、召回、纠错和遗忘”，再回答“一个需求能否可靠交付”，而不是只公布代码行数、模型调用数或测试总量。

Memory 建议分别记录有效召回、错误召回、纠错或删除后的残留、敏感信息越界与用户确认情况。开发闭环则分别跟踪：达到约定验收的任务比例、从需求到不同交付终点的耗时、人工介入次数、每次已验收交付的实际调用消耗、审查修复轮数、故障恢复耗时，以及失效授权和重复副作用被正确拒绝的情况。

这些指标尚未构成公开基准。不同任务复杂度、订阅与 API 计费来源、失败任务和未验收任务都应保留，不用单个成功演示代表总体效果。
