## 1. 状态机与流程管理

### 1.1 不能只有一个 `running / done` 字段

系统中的不同对象回答不同问题：

| 层次 | 回答的问题 | 典型对象或字段 |
| --- | --- | --- |
| 日常请求与 Agent 运行 | 这次输入处理到哪里，调用了哪些工具？ | Operation、Run、Step、Task |
| 开发需求整体 | 这个 Feature 处于哪一类交付状态？ | Feature、version、state、checkpoint |
| 具体业务动作 | 这一步处理哪份输入、采用哪份配置？ | WorkflowAction、输入绑定、执行快照 |
| 一次外部模型尝试 | 有没有派发，谁拥有本次执行，结果是否到达？ | ProviderAttempt、owner、fence、结果摘要 |
| 有效执行门 | 当前是否允许继续执行？ | ExecutionGate、approval epoch |
| 工作领取与权限时效 | 谁在执行，允许执行的范围和有效期是什么？ | WorkerJob、任务租约、策略租约、capability |
| 外部副作用与恢复 | 远端动作是否实际发生，有何证据？ | ExternalEffect、RecoveryCase、readback、receipt |
| UI 展示 | 用户看到什么进度和待决策项？ | Timeline、卡片、Decision Dock 等投影 |

阶段化是目标流程的重要组成，但不能把一个 `stage_id` 字段或产物摘要当作完整阶段状态机已经落地。阶段创建、依赖、失败、重试、提交及恢复必须形成可验证的持久链路。

### 1.2 Feature 的已定义状态

当前 Feature 合同包含以下状态组：

| 状态组 | 状态 |
| --- | --- |
| 需求与计划 | `intake`、`planning`、`awaiting_plan_review`、`approved` |
| 实现与审查 | `coding`、`verifying`、`reviewing`、`fixing`、`verified` |
| 后续交付事实 | `awaiting_merge`、`merged`、`deployed`、`completed` |
| 可区分的阻塞 | `blocked_requirement`、`blocked_usage`、`blocked_auth`、`blocked_test`、`blocked_external_prerequisite`、`blocked_unknown` |
| 核对与人工介入 | `reconciliation_required`、`needs_human`、`paused` |
| 取消终态 | `cancelled` |

这是一份**状态枚举分组，不是所有合法边的列表**。可达边、发起者、证据类型、guard 和原子写入集合由冻结的 transition registry 决定；不能因为两个状态在表里相邻，就假定可以直接跳转。

现有状态还保留了历史交付合同。后续产品层级和阶段化改进需要兼容设计，不应批量把历史 `succeeded` 或 `completed` 重新解释成更高等级的完成。

源码：[storage/models.py](../../src/personal_agent_dal/storage/models.py)、[registry.py](../../src/personal_agent_dal/machine/registry.py)。

### 1.3 谁可以改变状态

确定性引擎接收的是命令、预期版本、发起者、幂等键及可信解析器收集的证据，**不是模型指定的目标状态**。

一次迁移需要满足：当前状态匹配、命令被 registry 收录、角色与证据合法、guard 通过、当前版本符合预期。然后在同一个真实数据库事务中执行声明的写入集合并记录回执。

实现包含几条重要约束：

- 未定义的迁移拒绝；失败路径不留下部分业务写入。
- 使用 CAS，即“只有数据库仍是我预期的版本，才允许修改”。即使状态名称不变，也需要占用一个新版本。
- 精确重复命令可以重放原回执；同一幂等键携带不同意图不能作为新命令通过。
- `completed` 与 `cancelled` 不可随意退出；已经发生的 `merged / deployed` 外部事实不能用“取消”抹除。

这些约束见 [engine.py](../../src/personal_agent_dal/machine/engine.py) 与 [数据库模型](../../src/personal_agent_dal/storage/models.py)。

### 1.4 UI 进度只是投影

“正在审查”“等待确认”或“报告已生成”是面向用户的展示信息，不是授权源。显示成功的卡片不能推进数据库状态；过期卡片也不能因为仍留在 Timeline 中而继续批准旧内容。

状态机管理业务事实，投影帮助人理解业务事实，两者不能互相替代。

## 2. 授权管理：批准的是哪一次行动

### 2.1 分层授权

| 层次 | 作用 | 不能替代什么 |
| --- | --- | --- |
| 设备身份 | 确认请求来自已登记设备及有效会话 | 不代表该设备可以调用所有工具 |
| 业务 scope 与工具策略 | 限制可见、可调用的业务能力 | 不代表已经批准某个开发方案或外部写入 |
| 文档／决策审批 | 用户接受某份具体 PRD、方案、交付或续批请求 | 不代表接受后续任意修订 |
| Capability | 把批准转换为有限动作、范围、次数和时效 | 不代表 Worker 永久拥有同类权限 |
| 执行准入与租约 | 限制实际执行节点、所有权与有效时段 | 不代表批准新任务或更大的预算 |
| 外部动作授权 | 控制 commit、push、PR、merge、deploy 等具体副作用 | 不能用“任务已批准”一次性覆盖全部动作 |

设备身份更新、Worker token 续期、任务续批和能力授权是不同事件。**凭据恢复不产生新的业务批准；一个设备被撤销，也不能默认解释为历史上所有批准和外部副作用都已被撤销。** 当前系统对这几类对象分别处理，实际撤销效果必须逐项核对。

### 2.2 自然语言可以表达意图，不能伪造审批

模型可以帮助生成计划、解释风险、提出待审批事项，但审批应通过结构化通道提交，绑定用户实际看到的对象和版本。

对话中出现“同意”“继续”或某个文档自称“已批准”，不应绕过需要正式 gate 的动作。模型工具清单也不应包含能自行制造用户批准的能力。

### 2.3 审批绑定的不只是一个标题

状态绑定覆盖 Feature 身份、版本、状态、计划版本、仓库和 base、当前产物与已验证版本、决策前沿、策略版本、能力 epoch 及外部副作用清单等字段。

产物绑定则覆盖产物类型和版本、所属 Feature、base、正文规范化方式、正文摘要与大小、验收条件摘要、允许修改路径摘要等内容。

因此，下面这些看似“同一个任务”的情况，不能直接沿用同一份批准：

| 变化 | 为什么需要重新判断 |
| --- | --- |
| 文档标题没变，正文改了 | 用户批准的是旧内容，不是一个可变链接 |
| 计划未变，但切换了仓库或 base | 执行对象与上下文已不同 |
| 修复后候选代码发生变化 | 旧审查和旧交付接受不能直接证明新代码 |
| allowed paths 或验收条件改变 | 修改范围或完成标准已改变 |
| policy、capability 或决策版本失效 | 原授权可能已不适用于现在 |

服务器在消费审批的事务中重新构造当前状态，并从受保护的产物读取路径核对正文和摘要。客户端回传的是它观察到的摘要，不能把一个自行构造的“当前状态对象”交给服务端直接信任。

实现：[binding.py](../../src/personal_agent_dal/machine/binding.py)。

### 2.4 哈希、版本与身份各司其职

哈希用于绑定内容，CAS 版本用于发现并发变化，身份认证用于确定请求主体，审批与 capability 用于表达权限。**一个哈希相同不等于来源可信；一条请求签名有效，也不等于当前状态仍允许执行。**

同理，幂等键只解决“是否重复表达同一意图”，不能代替权限校验、结果验证和外部副作用核对。
