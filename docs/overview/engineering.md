## 1. 工程方法与验证体系

### 1.1 先冻结本轮目标，再实现

本仓库的工程约定采用：本轮 PRD → 明确批准 → 本轮技术方案 → 明确批准 → gate 记录 → 实现 → 验证 → 独立审查。

紧急修复、纯文档或纯测试可以遵循已有例外规则，但例外及原因必须记录。先实现后补审批，不等于满足流程；之前批准的大方向，也不能替代本轮尚未审阅的偏差。

这些协作规则约束的是开发者和开发 Agent。产品运行中的 DAL 审批则由运行时对象和协议承载，不能把 `AGENTS.md` 当成数据库授权系统。

### 1.2 分支、worktree 与稳定审查对象

分支隔离变更，worktree 支持并行工作目录，固定 base 和候选版本让审查可复现。共享文件的写入权仍需明确：多个 Agent 同时编辑同一工作区，会破坏“这次审查到底看的是哪份代码”的前提。

修复期间的检查点可以帮助恢复，但不等于已经完成阶段验收。合并、推送和部署分别记录实际动作与授权，不用本地提交替代对外发布事实。

### 1.3 验证分层

| 验证层 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| Schema 与冻结合同校验 | 字段、允许值、绑定和协议一致性 | 真实模型会遵守合同 |
| 单元与离线集成测试 | 已枚举分支、并发、事务和失败条件的行为 | 未覆盖的真实系统行为 |
| 合成输入的真实运行 | 指定环境中的协议、工具链和调用确实连通 | 所有真实业务任务都能完成 |
| 固定版本真实模型评测 | 指定样本、上下文、模型配置下的结果 | 跨模型、跨版本或跨场景的稳定优越性 |
| 真机与业务验收 | 用户路径在指定设备与范围内满足目标 | 全部异常、恢复、安全和生产规模边界 |
| 故障与恢复演练 | 指定失败下能正确停放、核对和继续 | 任意外部系统都能无损恢复 |

真实样本、用户复核的脱敏表达和合成样本需要明确区分，不能混为一个“准确率”。评测结果要绑定输入、上下文、期望和实际运行版本，旧样本上的成绩不能套到改过的样本上。

本项目文档不把历史测试总数作为质量评分，也不把源仓库曾经通过的测试声称为公开版本当前已重跑通过。

入口：[tests](../../tests/)、[evals](../../evals/)、AGENTS.md（原仓库路径：`AGENTS.md`）。

### 1.4 把失败形状放在正常路径旁边

需要重点覆盖的边界包括：空响应、畸形工具参数、一次出现多个不允许的调用、工具调用混入自由文本、被篡改的 provider 地址、凭据误发送、过期审批、重复派发、并发更新、Worker 失联、结果晚到、迁移中断和恢复后的旧快照。

在模型、网络和攻击者可控输入的边界上，mock 与代码可能共享同一个错误假设。离线全绿不能替代真实边界验证；真实验证也不能只选择最容易通过的一条 happy path。
